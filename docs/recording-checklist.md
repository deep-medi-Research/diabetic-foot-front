# 녹화 확인 체크리스트

<mark>**녹화 한 번이 분석에 쓸 수 있는지는 RGB 두 발 영상의 장 수, 카메라 단 누락, 저장 누락, 프레임 간격으로 먼저 판정하고, 그다음 열화상, PPG, 시각 맞춤, 카메라 설정을 봅니다.**</mark> 기준은 기본 촬영 선언 `specs/see3cam_manual_720p60.json`(1280x720, 60 fps, 1800장, 30초)입니다. 파일과 필드의 뜻은 [촬영 폴더](shot-folder.md)에 있습니다.

기준의 출처는 세 가지입니다. 코드가 이미 쓰는 값, 실험에서 정한 값, 아직 정하지 않은 값입니다. 표의 "출처" 열이 이것을 구분합니다.

| 출처 | 뜻 |
| --- | --- |
| 코드 | 앱이 그 값으로 판정하거나 표시함 |
| 결정 | 실험 결과로 정했지만 앱은 판정하지 않음 |
| 미정 | 값을 정하지 않음. 기록만 하고 이상한 값을 본다 |

## 1. 녹화 직후 화면

<mark>**메인 화면과 열화상 창의 "카메라 단 누락 N 저장 누락 N"이 둘 다 0이 아니면 그 촬영은 다시 찍습니다.**</mark> 0보다 크면 글자가 경고 색으로 바뀝니다(`app/qml/Main.qml`, `ThermalPane.qml`).

- [ ] RGB 카메라 단 누락 0
- [ ] RGB 저장 누락 0
- [ ] 열화상 카메라 단 누락 0, 저장 누락 0
- [ ] PPG 창에 "PPG 장치가 응답하지 않습니다"가 뜨지 않음. 앱은 1초마다 응답을 확인합니다(`app/src/ppg_controller.cc`)
- [ ] 결과 창 "프레임 간격" 줄이 경고가 아니고 "1초 창 최저 60 fps"에 가까움

카메라 단 누락이 있어도 앱은 1800장을 채울 때까지 더 찍습니다. 그래서 장 수가 맞아도 누락이 있을 수 있고, 2026-11-03 140040 촬영은 1800장을 31.3초에 찍었습니다. 누락이 있는 촬영은 쓰지 않기로 했습니다(2026-11-02). 그날 비교에서 맥박 주파수가 1~2% 달라졌고 누른 발 PI가 최대 2배 달라졌기 때문입니다.

## 2. RGB 발 영상 사이드카

`<ts>_left.json`과 `<ts>_right.json`을 각각 봅니다.

| 확인 | 필드 | 기준 | 출처 |
| --- | --- | --- | --- |
| 장 수 | `frames.written` | `frames.target`(1800)과 같음 | 결정 |
| 좌우 장 수 | 두 파일의 `frames.written` | 같음 | 결정 |
| 카메라 단 누락 | `frames.missing` | 0 | 결정 |
| 저장 누락 | `frames.dropped` | 0 | 결정 |
| 간격 중앙값 | `frames.median_interval_us` | 16,667 ±5% | 코드 |
| 느린 간격 | `frames.slow_intervals` | 0 | 코드 |
| 1초 최저 fps | `frames.min_fps_1s` | 60 | 미정 |
| 쓰기 대기열 | `frames.max_queue_frames` | `frames.buffer_frames`(120) 미만 | 코드 |
| 녹화 길이 | `last_time_us - first_time_us` | 약 30초 | 결정 |

- **누락과 느린 간격의 경계는 주기의 배수로 정해져 있음**<br>간격이 주기의 1.5배를 넘으면 누락으로 세고, 1.2배 초과 1.5배 이하이면 느린 간격으로 셉니다(`core/src/timing/frame_gap.cc`). 누락이 있으면 `frames.gaps`에 어느 프레임 뒤에 몇 장이 빠졌는지 남습니다
- **간격 5% 검사는 녹화를 시작할 때만 함**<br>최근 간격 중앙값이 선언 주기와 5% 넘게 다르면 앱이 녹화를 시작하지 않습니다(`platform/src/capture.cc`). 녹화 중에 fps가 떨어진 것은 이 검사가 잡지 못하므로 사이드카에서 봅니다
- **USB 2 포트면 15 fps로 잡힘**<br>RGB 카메라가 USB 2에 꽂히면 1280x720이 15 fps까지만 나와 녹화가 시작되지 않습니다. 앱이 USB 3 포트에 꽂으라고 안내합니다
- **저장 누락은 디스크에서 생김**<br>2026-11-02 노트북 SSD가 쓰기를 10~27초 멈춰 1080p60 14회 중 6회에서 대기열 120장이 차고 프레임을 버렸습니다. 메모리 쓰기 대기열(기본 768 MB)을 넣은 뒤로는 0입니다. `<ts>_left.mkv.queue.txt`의 `max_queued_mb`, `producer_wait_ms`, `mux_failed`가 이 대기열의 기록입니다

## 3. 프레임 시각

같은 사이드카의 `per_frame` 배열과 `clock`을 봅니다.

| 확인 | 필드 | 기준 | 출처 |
| --- | --- | --- | --- |
| 번호 연속 | `per_frame.index` | 1씩 증가 | 미정 |
| 시각 증가 | `per_frame.common_time_us` | 모든 간격이 0보다 큼 | 미정 |
| 카메라 시각과 수신 시각 | `device_time_us`, `host_time_us`의 간격 | 같은 곳에서 함께 벌어짐 | 미정 |
| 시계 맞춤 잔차 | `clock.max_residual_us` | 기록만 함 | 미정 |
| 시계 속도 | `clock.rate` | 1에 가까움 | 미정 |

- **번호는 스트림을 연 뒤 받은 순서**<br>`per_frame.index`는 녹화가 시작되기 전에 받은 프레임 수만큼 큰 번호에서 시작하므로 0이 아닙니다. 1씩 늘어나는지만 봅니다
- **공통 시각은 PC 시계로 옮긴 카메라 시각**<br>공통 시각 = `offset_us` + `rate` x 장치 시각이고 단위는 마이크로초입니다. RGB는 카메라가 붙인 시각을 PC가 받은 시각에 직선으로 맞춥니다
- **누락이 카메라에서 생겼는지는 카메라 시각으로 가림**<br>`device_time_us`에도 같은 간격이 있으면 카메라가 프레임을 보내지 않은 것입니다. 2026-11-03 720p60 10건 중 2건이 이 경우였고 매번 116.7 ms(6장)가 빠졌습니다. 카메라 시각은 고르고 `host_time_us`만 벌어지면 PC 쪽(USB, 드라이버, 앱)에서 늦은 것입니다
- **잔차와 시계 속도는 실기에서 잰 적 없음**<br>합성 데이터에서는 공통 시각 오차가 1 ms 안이었습니다([00-architecture.md](00-architecture.md)). 실기 값의 범위를 모르므로 기준을 정하기 전까지 값을 기록해 둡니다

## 4. 열화상

`<ts>_thermal.json`과 열화상 파일을 봅니다. 열화상은 9 Hz(`thermal_record_period_us` 111111)로 30초에 270장을 기록합니다.

| 확인 | 필드 | 기준 | 출처 |
| --- | --- | --- | --- |
| RGB 구간 안 장 수 | `frames.written_in_rgb_window` | 225 이상 | 코드 |
| 누락 | `frames.missing + frames.dropped` | 0 | 코드 |
| 파일 크기 | `_thermal.raw16` 크기 ÷ 614,400 | `frames.written`과 같음 | 미정 |
| 발 영역 파일 | `thermal_left.npy`, `thermal_right.npy` | 둘 다 있음, 첫 차원이 `frames.written` | 미정 |
| 카메라 온도 기록 | `_thermal_camera_temp.csv` 줄 수 | `frames.written`과 같음(파일이 있을 때) | 미정 |

- **225장 미만이나 누락은 분석 전에 경고만 함**<br>분석 입력 검사(`core/src/record/analysis_inputs.cc`)는 열화상 파일이 없거나, 225장 미만이거나, 누락이 있으면 경고하고 분석은 진행합니다
- **열화상 시각은 PC가 받은 시각**<br>열화상 SDK는 프레임에 장치 시각을 주지 않아 수신 시각을 장치 시각으로 씁니다. 그래서 열화상의 시각 맞춤 오차는 열화상 파일만으로 확인할 수 없습니다

## 5. PPG

PPG를 연 촬영에만 `<ts>_ppg.csv`와 `<ts>_ppg.json`이 있습니다. PPG는 500 Hz입니다.

| 확인 | 필드 | 기준 | 출처 |
| --- | --- | --- | --- |
| 표본 누락 | `samples.missing`, `samples.gaps` | 0, 비어 있음 | 미정 |
| 표본 간격 | `samples.median_interval_us` | 2,000 | 미정 |
| RGB 구간 안 측정 오류 | `measure_errors.rgb_window` | 오류 표본 0 | 미정 |
| 통신 오류 | `link.crc_failures`, `bad_lengths`, `implausible`, `skipped_bytes` | 0 | 미정 |
| 끊김(장치 오류 메시지) | `events`에서 `code`가 `e`인 것 | 0건 | 미정 |
| CSV 줄 수 | `_ppg.csv` 줄 수 - 1 | `samples.count`와 같음 | 미정 |

- **연결이 끊긴 시각은 사이드카에 없음**<br>`events`는 장치가 보낸 상태와 오류 메시지만 담습니다. PPG 연결이 녹화 중에 끊기면 앱이 촬영 결과 줄에 끊긴 시각을 적고, 사이드카에서는 PPG 표본이 RGB 구간 끝보다 먼저 끝나는 것으로 드러납니다(6절)
- **측정 오류 코드는 손가락과 센서 상태**<br>`measure_error`가 0이면 정상이고, 102는 손가락 빠짐, 115는 신호 나쁨, 112는 센서 연결 안 됨입니다
- **PPG는 RGB보다 길게 기록함**<br>촬영 버튼부터 저장까지 기록하고 안정 대기도 들어가므로 `samples.count`는 RGB 30초보다 많습니다. RGB 녹화 구간 안의 표본은 `measure_errors.rgb_window.samples`가 셉니다
- **PC 포트에 바로 꽂으면 멈춘 적이 있음**<br>PPG 센서는 USB 허브를 거쳐 연결합니다. PC 포트에 바로 꽂았을 때 측정이 1초 안에 멈춘 적이 있습니다

## 6. 장치 사이 시각

<mark>**RGB 두 발, 열화상, PPG의 공통 시각이 같은 30초를 덮는지 봅니다.**</mark> 네 기록의 공통 시각은 같은 PC 시계입니다.

- [ ] 왼발과 오른발 RGB의 첫 `common_time_us` 차이가 한 프레임 주기(16.7 ms) 안. 두 발 영상은 같은 카메라 프레임을 잘라 쓰므로 같아야 합니다
- [ ] 열화상 공통 시각의 첫 값과 마지막 값이 RGB 녹화 구간을 덮음
- [ ] PPG `_ppg.csv`의 `common_time_us`가 RGB 녹화 구간을 덮음
- [ ] PPG와 RGB 시각 차이는 기준 미정. PC가 받은 시각 기준이라 USB 수신 지연만큼 어긋날 수 있고, 실기에서 잰 적이 없습니다

## 7. 카메라와 조명 설정

사이드카의 `settings`와 `light`가 촬영 선언과 같은지 봅니다.

| 확인 | 필드 | 기준 | 출처 |
| --- | --- | --- | --- |
| 노출 방식 | `settings.mode` | `manual` | 결정 |
| 노출 | `settings.exposure_step` | -9 | 결정 |
| 게인 | `settings.gain` | 1 | 결정 |
| 화이트 밸런스 | `settings.white_balance_k` | 4000 | 결정 |
| 설정 고정 | `settings.locked` | 참 | 결정 |
| 조명 적용 | `light.response` | `applied` | 미정 |
| 깜빡임 | `light.flicker.periodic_fraction` | 기록만 함 | 미정 |

- **조명 적용은 앱이 조명을 제어할 때만 봄**<br>`light.source`가 `app`일 때만 `light.response`를 판정합니다. `external`이면 앱이 조명에 명령을 보내지 않아 반응을 볼 수 없습니다
- **자동 노출은 fps를 떨어뜨림**<br>2026-10-16 어두운 장면에서 카메라 자동 노출이 fps를 15로 내렸습니다. 수동 노출로 찍어야 합니다
- **앱은 설정을 기록만 함**<br>사이드카의 설정을 촬영 선언과 견주는 코드는 없습니다

## 도구로 확인하기

<mark>**`tools/check_shot.py`가 촬영 폴더 하나를 읽어 2절부터 8절까지의 항목을 PASS, FAIL, WARN, SKIP으로 판정하고, FAIL이 하나라도 있으면 종료 코드 1을 냅니다.**</mark> 파이썬 3.9 이상의 표준 라이브러리만 씁니다. 항목 이름은 이 문서의 표와 같습니다.

```bash
python3 tools/check_shot.py <촬영 폴더>
python3 tools/check_shot.py <촬영 폴더> --json
```

- **판정 규칙**<br>출처가 코드나 결정인 항목은 어기면 FAIL이고, 미정인 항목은 어겨도 WARN입니다. 이 촬영에 없는 파일(PPG, 카메라 온도)이나 오래된 사이드카에 없는 필드는 SKIP이고 이유가 함께 나옵니다. 폴더를 읽을 수 없으면 종료 코드 2입니다
- **기준은 촬영에서 얻음**<br>목표 장 수는 사이드카의 `frames.target`입니다. fps는 매니페스트가 가리키는 촬영 선언(`specs/`)에서 읽고, 선언을 읽지 못하면 사이드카의 `format.frame_rate`를, 그것도 없으면 간격 중앙값을 씁니다. 그래서 30 fps 촬영도 같은 명령으로 봅니다
- **허용 폭은 도구가 정함**<br>이 문서가 숫자를 정하지 않은 곳에 도구가 허용 폭을 넣었습니다. 녹화 길이와 PPG 표본 간격은 선언 값의 5% 안, 1초 최저 fps는 선언 값의 95% 이상, 시계 속도는 1에서 0.1% 안, 열화상이 RGB 구간에서 벗어나도 되는 폭은 열화상 기록 주기입니다. 미정 항목이면 WARN만 냅니다
- **6절과 8절의 출처**<br>이 두 절에는 출처 열이 없어 도구가 정했습니다. 두 발 첫 프레임 시각 차이와 8절의 두 항목은 결정이고, 열화상과 PPG가 RGB 구간을 덮는지는 미정입니다
- **큰 파일은 열지 않음**<br>영상과 열화상 원시값은 크기만 보고, `.npy`는 머리글만 읽습니다
- **도구가 보지 못하는 것**<br>1절의 화면 표시, 카메라가 발을 실제로 보고 있는지, 영상의 화질, PPG와 RGB의 시각 차이는 사람이 봅니다. PPG와 RGB의 시각 차이는 두 기록에 같이 찍힌 사건이 없어 파일만으로 잴 수 없습니다
- **시험**<br>`python3 tools/test_check_shot.py`는 작은 가짜 촬영 폴더로 판정을 확인합니다
